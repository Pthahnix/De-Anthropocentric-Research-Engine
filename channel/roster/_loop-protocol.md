# 循环协议（全员共用）

每个岗位除自己的 `roster/<代号>.md` 外，必须读本文件。
本文件规定：什么时候醒、阻塞时做什么、怎么声明完成、什么时候休眠。

## 一、你处于 goal 模式

你不是接一个任务然后交差。你的 goal 是「本岗位职责范围内的设计工作全部完成
且被 Sirelia 批准」。在此之前你持续工作，反复读写 channel，与其他岗位交互。

**goal 达成的唯一判据：Sirelia 在 `00-escalation.md` 里明确写下
「[Sirelia → <你的代号>] GOAL ACHIEVED」。** 你自己认为做完了不算达成，
只算「提交完成声明」。

## 二、工作节奏：长块，不是轮询

**错误的节奏：** 每几分钟读一次 channel，没新东西就写一条「仍在等待」。
这是空转，污染频道，浪费预算。

**正确的节奏：**

1. 读 channel（一次，读全）
2. 判断当前能推进的最大工作块是什么
3. **完整做完这个块**（不中途刷频道）
4. 交付 + 发言
5. 回到 1

一个「工作块」的粒度参考：R2 审 20 条 contract、R4 修完一类缺陷、
R1 写完一个子规格。不是「审 1 条」「改 1 个字段」。

## 三、唤醒条件（写死，按岗位）

| 岗位 | 唤醒条件 |
|---|---|
| R1 | 无（不被任何人阻塞，持续工作至完成） |
| R2 | 无（幻影 mode + object mismatch 不依赖他人）。仅 MOVED_RUNTIME 那 7 条等 R1 落锤 |
| R4 | 无（修补工作全部可独立推进） |
| R3 | 无（用户侧调研先做）。catalog 机制的**终稿**等 R1 |
| R5 | 无（字段分布分析 + 投机分支规格先做）。**塌缩**等 R1 |

**注意：没有任何岗位的唤醒条件是「等别人」。** 所有人都有立即可做的工作。

## 四、被阻塞时的强制动作

如果你发现某个决策依赖别人还没给的答案，**不许停下等**。按顺序尝试：

### 第一选择：投机分支

把依赖项的可能取值枚举出来，对每个取值都产出成立的设计。

例：R5 不知道 contract 字段落在哪（frontmatter / capabilities.json / body），
就写一份三分支的映射规格。三个分支共用的部分（threshold 保留规则、
N-to-1 合并顺序、rubric 分配）一次写完；分歧的部分（字段语法、解析方式）
分三小节写。R1 落锤后删掉两个分支即可。

**投机分支的成本远低于串行等待。** 三个分支通常共用 70-90% 的内容。

### 第二选择：换工作块

如果投机分支代价确实过高（分支数 > 4，或分支间无共用内容），
切到本岗位另一个不依赖该决策的工作块。

例：R3 的 catalog 选型等 R1，但冷启动场景收集、v3 流程对比、
`ResearchContext` 处理方案（这个不依赖 Spec 归属）都能先做。

### 第三选择：求裁

前两条都走不通，才写进 `00-escalation.md`：

```
## [<你的代号> → Sirelia] 求裁 2026-09-xx

阻塞项：<一句话>
依赖谁：<代号或「未定」>
为什么不能投机分支：<理由，要具体>
为什么不能换工作块：<本岗位剩余工作块清单，说明为何都被同一决策阻塞>
我建议的答案：<你自己的倾向 + 理由>
```

**注意最后一行是必填的。** 求裁不是把问题扔回来，是带着你的判断来要一个确认。

## 五、三种发言，三个去处

| 类型 | 写到哪 | 我会不会立刻看到 |
|---|---|---|
| 交付物 | `deliverables/<代号>/` | 不会。在话题帖里贴路径通知 |
| 岗位间协作 | `channel/<NN>-<topic>.md` 追加 | 不会。我批量扫 |
| **求裁 / 完成声明** | `channel/00-escalation.md` | **会。我挂了监听** |

`00-escalation.md` 只放三类：求裁、完成声明、闸门解除。
**日常进度、交付通知、岗位间讨论不许写进去。** 那会让监听失效。

## 六、完成声明

你认为本岗位工作全部完成时，写进 `00-escalation.md`：

```
## [<你的代号> → Sirelia] 完成声明 2026-09-xx

交付物清单：
- <路径> — <一句话说明>
- <路径> — <一句话说明>

验收标准对照：
| roster 里的验收要求 | 我的交付 | 证据 |
|---|---|---|
| <要求 1> | <做了什么> | <文件:行号 / 节点 ID> |

已知未解决项：
- <项目> — <为什么留着，交给谁>

自评：<哪部分最弱，你自己最不确定的是什么>
```

**「已知未解决项」和「自评」两栏不许写「无」。** 任何设计工作都有留尾巴
和不确定的地方；写「无」我一律驳回。

发完声明后你休眠。我会：
- 批准 → 写 `GOAL ACHIEVED`，你结束
- 驳回 → 列出具体返工项，你被重新唤醒，只做返工项

## 七、不许做的事（全员）

1. **不许空转发言。** 「我正在读文件」「仍在等待 R1」这类没有信息量的帖子
   一条都不许发。没进展就别发言，去做事。
2. **不许替别人做决定。** 发现别人岗位的问题，写成给那个岗位的发言，
   不要自己动手改他的交付物。
3. **不许因为别人慢就降低自己的标准。** 尤其 R2：审计标准不因时间线松动。
4. **不许写 secret / API key** 进任何文件，示例也不行。
5. **不许在 `00-escalation.md` 里聊天。**

## 八、一条给 R1 的额外规定

**R1 不等 R2。** 你重判 7 条 MOVED_RUNTIME 时，从第一原理判（这件事在职责上
属于运行时还是产品层），不要等 R2 告诉你这些 contract 本身有没有坏。
如果 R2 事后推翻了其中某条，那是一张返工单，不是你现在停下的理由。

你是唯一的 P0 闸门持有者。你的速度决定整个项目的速度。

## 九、全程禁用的 skill（全员，无例外）

**本项目全程禁用两套 skill：**

1. **`superpowers`**（及其全部子 skill：brainstorming、writing-plans、
   subagent-driven-development、systematic-debugging、condition-based-waiting 等）
2. **`ara` / `ara-from-context` / `ara-commons` 系列**（compiler、rigor-reviewer、
   Seal Level 审查等）

### 为什么

- **superpowers**：它的 brainstorming / writing-plans 会把你的产出改造成它自己的
  模板结构。本项目的交付物格式由你的 roster 文件规定，不由插件规定。
  它的 subagent-driven-development 会让你把工作外包给你控制不了的子 agent，
  而你的 roster 明确规定了「不许扩张边界」。
- **ara**：ARA 是 DARE 的**设计对象**，不是本项目的**工作工具**。
  你在设计 ARA 该长什么样，不要用现有的 ARA 编译器去编译你的设计文档——
  那会把「被设计的东西」和「设计所用的工具」混在一起。

### 读 ≠ 调用

**读 ARA 相关文件是允许的，而且对某些岗位是必须的。**

- R1 必须读 `skills/ara-from-context/SKILL.md`（了解 AI 专读的成果是什么形状）
- R5 可能要读 ARA 的正文结构作为参考

**禁的是 `Skill` 调用**，即不许 load / invoke / 执行这些 skill。
用普通的文件读取工具去读它们的 SKILL.md，随便读。

### 违反的后果

如果你的交付物里出现了 superpowers 的模板痕迹（如 brainstorming 的
「Let me explore the design space」段落结构、writing-plans 的固定章节名）
或 ARA 的四层结构（logic/ src/ trace/ evidence/），一律驳回重做。

你的交付物格式只由你的 roster 文件和本协议规定。
